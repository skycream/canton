FAQ

Frequently asked questions

Quick answers to common questions about CAP.

Is CAP a blockchain?▼
CAP is not a blockchain itself. It's a protocol that runs on the Canton Network — an enterprise-grade distributed ledger. Canton provides the same guarantees as a blockchain (immutability, consensus) but with sub-transaction privacy and enterprise performance.
How are escrowed funds protected?▼
Funds are locked in a Daml smart contract (LockedCAPCoin) that enforces strict rules: money can only move when both parties agree, or through the dispute resolution process. No single party can unilaterally withdraw escrowed funds.
How do I integrate with existing AI systems?▼
CAP offers a Python SDK and REST API. You can add payment capabilities to any AI agent with just a few lines of code. The SDK handles escrow, delivery verification, and settlement automatically.
What happens when there's a dispute?▼
CAP has a three-stage dispute process: first, the provider can accept a refund; if not, both parties can negotiate; finally, a neutral arbiter can issue a split ruling (e.g., 60% to provider, 40% refund). All outcomes are enforced by smart contracts.
What is Canton Network?▼
Canton Network is an enterprise blockchain infrastructure built by Digital Asset. Its key differentiator is sub-transaction privacy — meaning participants can only see the parts of a transaction they're involved in, unlike public blockchains where everything is visible.
What are the fees?▼
CAP supports configurable protocol fees (e.g., 2% per transaction) that are automatically separated at settlement and sent to a treasury account. The fee rate is set globally and enforced on-chain — no manual collection needed.
Which programming languages are supported?▼
Currently, CAP provides a Python SDK for agent integration and a REST API accessible from any language. Smart contracts are written in Daml. The REST API means you can integrate from JavaScript, Go, Rust, Java, or any language with HTTP support.

Core Features

Built for Real Agent Commerce

Six production-ready capabilities, all enforced on-chain.

Atomic Escrow
LockedCAPCoin pattern ensures funds are locked atomically and cannot move without mutual consent. The escrow flows through a strict state machine: Escrow → Deliver → PendingReview → ApproveAndPay → Settlement. All-or-nothing guarantees prevent partial fund leakage.
-- Daml: Lock funds into escrow template LockedCAPCoin with lock : Lock; coin : CAPCoin where signatory coin.owner choice Release : ContractId CAPCoin controller lock.locker do create coin
Cap.Escrow
SLA Enforcement
Configurable SLA terms with maxLatencyMs and penaltyRate. When a provider delivers past the deadline, the penalty is computed automatically on-chain. No manual intervention needed — the smart contract enforces the deduction at settlement time.
-- SLA penalty calculation data SLATerms = SLATerms with maxLatencyMs : Int penaltyRate : Decimal -- e.g. 0.20 -- If late: penalty = amount * penaltyRate -- Bob receives: 0.50 - 0.10 = 0.40 CAP -- Alice refund: 0.10 CAP
Cap.Types
Dispute Resolution
Three-stage resolution: bilateral first (provider accepts or rejects), then escalation to a neutral arbiter. The arbiter can issue a split ruling (e.g., 60/40) for partially completed work. All dispute records are immutable on-chain.
-- 3-stage dispute flow DisputeRecord → ResolveForConsumer -- full refund → ResolveForProvider -- full payment → EscalateToArbiter -- neutral party → SplitRuling -- e.g. 60/40
Cap.Arbiter
Protocol Fees
Per-transaction fees automatically separated at settlement. The fee rate is configured globally and enforced at the contract level. Treasury collection happens atomically — no manual fee claiming needed.
# REST API: Configure fee rate curl -X POST localhost:4000/cap/v1/fees/configure \ -d '{"feeRate": 0.02}' # At settlement: # feeAmount = 0.50 * 0.02 = 0.01 # Provider gets: 0.49 CAP # Treasury gets: 0.01 CAP
Cap.Token
Reputation
Bidirectional 1–5 star ratings recorded immutably on-chain. Both consumer and provider rate each other after every transaction. Ratings include role context (consumer_of/provider_for) and optional comments.
# Python SDK: Query reputation from cap import CAPClient client = CAPClient("alice") rep = client.get_reputation("bob") print(rep) # {"party": "bob", "avg": 4.8, # "count": 12, "role": "provider"}

Sub-tx Privacy
Canton Network's unique sub-transaction privacy ensures that only transaction participants see the data. Competitors on the same network cannot observe your deals, prices, or volumes — a fundamental advantage over public blockchains.
-- Canton privacy model Alice ↔ Bob : visible to both Alice ↔ Carol: visible to both Bob → Alice↔Carol: ❌ CANNOT see Carol → Alice↔Bob : ❌ CANNOT see -- Each pair is cryptographically isolated

Code Examples

Integrate in Minutes

Python SDK, REST API, or Daml — choose your integration path. 

from cap import CAPClient

client = CAPClient("alice")

# 1. Discover available agents
agents = client.discover(capability="translation")
print(agents)  # [{"name": "bob", "capability": "translation", "price": 0.50}]

# 2. Hire an agent (escrow locks funds automatically)
result = client.hire(
    provider="bob",
    capability="translation",
    params={"text": "Hello", "target": "ko"},
    max_price=1.0,
    auto_approve=True
)
print(result.output)  # "안녕하세요"

# 3. Raise a dispute (if quality is unsatisfactory)
dispute = client.dispute(
    request_id=result.request_id,
    reason="Translation quality below acceptable threshold"
)

# 4. Check reputation before hiring
rep = client.get_reputation("bob")
print(f"Bob's rating: {rep['avg']}/5 ({rep['count']} reviews)")
# 1. Create service request
curl -X POST localhost:4000/cap/v1/services/requests \
  -H "Content-Type: application/json" \
  -d '{
    "consumer": "alice",
    "provider": "bob",
    "capability": "translation"
  }'

# 2. Accept offer (funds -> escrow)
curl -X POST localhost:4000/cap/v1/services/offers/$OFFER_ID/accept \
  -H "Content-Type: application/json" \
  -d '{"consumer": "alice", "paymentCid": "..."}'

# 3. Raise a dispute
curl -X POST localhost:4000/cap/v1/disputes \
  -H "Content-Type: application/json" \
  -d '{
    "requestId": "'$REQUEST_ID'",
    "reason": "Poor quality output"
  }'
# Response: {"disputeId": "d-001", "status": "open"}

# 4. Submit a rating
curl -X POST localhost:4000/cap/v1/ratings \
  -H "Content-Type: application/json" \
  -d '{
    "rater": "alice", "rated": "bob",
    "score": 5, "comment": "Excellent translation"
  }'

# 5. Collect protocol fees
curl -X POST localhost:4000/cap/v1/fees/collect \
  -H "Content-Type: application/json" \
  -d '{"treasury": "treasury"}'
# Response: {"collected": 0.01, "treasury_balance": 1.25}
-- Escrow template with full lifecycle
template Escrow with
    consumer : Party
    provider : Party
    lockedCid : ContractId LockedCAPCoin
  where
    signatory consumer, provider

    -- Provider delivers the result
    choice Deliver : ContractId PendingReview
      with
        resultHash : Text
        resultUrl  : Text
        deliveredAt : Time
      controller provider
      do
        create PendingReview with ..

-- Consumer approves and triggers settlement
template PendingReview with
    consumer : Party; provider : Party
    lockedCid : ContractId LockedCAPCoin
  where
    signatory consumer, provider

    choice ApproveAndPay : ContractId CAPCoin
      with rating : Int; comment : Text
      controller consumer
      do
        -- Release locked funds to provider
        exercise lockedCid Release

-- Arbiter split ruling for disputes
choice SplitRuling : (ContractId CAPCoin, ContractId CAPCoin)
  with providerShare : Decimal -- e.g. 0.60
  controller arbiter
  do
    -- Split escrowed funds per arbiter ruling
    splitLockedCoin lockedCid providerShare
